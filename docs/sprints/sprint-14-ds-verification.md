## 작업 항목

### 문항 데이터: 검증 방식 표시 (`verify`)

- [x] 데이터과학 문항마다 검증 방식을 정한다: **실행**(`run`) · **실행 제외**(`skip`, 이유 필수) · **개념**(코드 없음)
  - `code-write`: 항상 실행(실행 제외 불가)
  - `code-blank`·코드가 있는 `mcq`·`multi`·`blank`: `verify` 필수 — 실행이면 실행 환경(Python 패키지·준비 코드, SQL 스키마)과 검사 종류, 실행 제외면 이유
  - 코드가 없는 문항: 개념
- [x] 실행할 수 없는 코드(셀레니움·Colab 명령·MySQL 서버 전용 문법)는 실행 제외 + 이유를 **강제**: 감지 규칙에 걸리는데 `run`이면 실패, `skip`인데 실제로 실행되는 코드면 실패
- [x] MySQL 전용 SQL(실행 제외)은 **빈칸형·개념형으로만** 허용(`code-write`·출력 고르기 금지)

### 대상별 실행 검증

- [x] **전체 작성형**: 모범 답안이 오류 없이 실행되고, 값 검사(`checks`)를 통과하고, 문항에 적은 기대 결과(슬라이드 실행결과 — Python 표준 출력, SQL 결과 표)와 같다
- [x] **코드 빈칸형**: 각 빈칸의 모든 허용 답안을 끼운 전체 코드가 실행되고 **모두 같은 결과**(표준 출력·값 검사·오류 여부, SQL은 결과 표·테이블 상태)를 낸다. 대표 오답(`wrong`)은 다른 결과
  - 허용 답안 후보: (a) **공통 변환 규칙 목록**으로 첫 번째 정답에서 후보를 만들고 (b) 문항 작성자가 후보(`candidates`)를 더한다 → 실행해서 같은 결과면 `accept`에, 다르면 `wrong`(오답 예시)에 **들어 있어야** 통과(빠진 것은 테스트가 "추가하라"고 알려 준다. 데이터를 자동으로 고쳐 쓰지 않는다)
  - 토큰 비교로 이미 같은 후보(따옴표 종류·공백·SQL 키워드 대소문자)는 `accept`에 넣지 않는다(중복 금지 규칙 — Sprint 12)
  - **슬라이드 표기를 첫 번째 정답으로** 둔다: 후보는 첫 번째 정답에서 만들고, 대조 기록에 슬라이드 표기를 남긴다
- [x] **코드 출력 고르기**(`mcq`·`multi`·`blank`에 코드): 실제 실행 결과가 정답 보기와 같고 오답 보기와는 다르다(`multi`는 정답 보기가 모두 출력 줄에 있고 오답 보기는 없음). 오류 위치 문제는 실제 오류 종류·줄 번호와 비교
- [x] **실행마다 달라지는 출력**(세트 순서·해시·시간·난수): 해시 시드를 바꾼 엔진(PYTHONHASHSEED 1·2)과 같은 엔진 두 번 실행의 출력이 하나라도 다르면 실패 — "출력 문제로 쓸 수 없음"
- [x] **SQL**: 문항마다 스키마·초기 데이터로 실행해 결과 표·테이블 상태를 검증. `#` 주석은 런타임 규칙대로 `--`로
- [x] **슬라이드 오류 목록**(2-10 콜론 누락, 2-20·2-21 세트 순서, 2-22·2-24·6-1 출력 표기 차이, 6-40 실행 순서, 6-4 플랫폼 차이)을 쓰는 문항은 해설에 **"(보충)"**과 슬라이드와 다른 점(목록에 적은 핵심어)이 있어야 한다

### 기록

## 마무리 때 더한 규칙 (2026-10-06)

- **기준 실행 환경**: 정답 기준은 슬라이드(Colab) 환경이다. Pyodide와 결과가 달라질 수 있는 출력(넘파이 dtype·정수 크기, 플랫폼 의존 표기)은 출력 문제로 내지 않는다(`ds-question-types.md` 결정 15). 감지: 출력 문제(전체 작성형·출력 고르기) 코드의 `.dtype`·`.itemsize`·`.nbytes`·`sys.maxsize`·`sys.platform`·`sys.version`·`platform.`·`os.name`·`id(`·`getsizeof(`(실행 없이), 실행 출력의 `int32`·`uint32`·메모리 주소 `0x…`(실행 검증)
- **오류 줄 번호**: 앱 화면 코드(빈 줄 포함) 기준(결정 16). 검증은 화면 코드를 그대로 실행하므로 Python 오류 줄 = 화면 줄. 줄을 묻는 문항은 `lineNumbers: true`, 그 줄이 빈 줄이거나 범위 밖이면 실패. [코드 2-10] 전사는 슬라이드(Lec2 s.17 그림)의 2번째 줄 빈 줄을 보존해 `else`가 **12번째 줄**(처음 보고한 11은 빈 줄을 빼고 옮긴 코드 기준이었다 — 고침)

## 문서와 다르게 한 부분

- 해시 시드를 바꾼 실행(세트 순서 검출)과 판다스 문항 검증은 `npm test`가 아니라 `npm run verify:ds`에서만 돈다 — 한 번에 돌리면 60초를 넘고 기존 엔진 테스트가 시간 초과로 깨졌다. `npm test`는 같은 엔진 두 번 실행만(난수·시간은 잡고 세트 순서는 못 잡음)
- 코드 출력 고르기·오류 검사(`check`)는 **Python만** 지원. SQL 결과를 고르는 보기 문제는 `code-write`·`code-blank`로 내거나 다음에 추가한다
- "슬라이드 표기를 첫 번째 정답으로"는 데이터에 슬라이드 원문이 없어 자동으로 확인할 수 없다 → 후보를 첫 번째 정답에서만 만들고, 대조 기록·검토로 확인한다
- 빈칸이 여러 개면 한 칸씩 바꿔 실행한다(나머지 칸은 첫 번째 정답). 모든 조합은 실행하지 않는다
- 검증 코드는 `ds-question-types.md` §6-2 계획의 `data/subjects/data-science/*.test.ts`가 아니라 `lib/verify/`에 두었다 — playground 예시·틀린 데이터·대조 기록을 같은 곳에서 다루기 위해서
