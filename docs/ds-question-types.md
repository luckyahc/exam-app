## 2. 코드 빈칸형 `code-blank`

데이터(안): `{ language, code: "여러 줄 코드, 빈칸 자리는 {{0}} {{1}}", blanks: [{ accept: string[] }], wrong?: string[][] }`. 들여쓰기·나머지 코드는 고정이고 빈칸만 입력한다.

### 2-1. 채점 방식 비교

| | (A) 빈칸별 허용 답안 비교 | (B) 빈칸을 채운 전체 코드 실행 |
|---|---|---|
| 방법 | 입력을 정해진 규칙(§2-2)으로 정규화해 `accept` 목록과 비교 | 빈칸을 끼운 코드를 Pyodide/sql.js로 실행해 출력·상태를 모범 답안과 비교 |
| 동치 답 처리 | 목록에 있는 것만 정답(`i <= 9`를 정답으로 두면 `i < 10`은 목록에 넣어야 정답) | 실행 결과가 같으면 모두 정답 |
| 엔진 | 필요 없음 — 즉시 채점, 오프라인, 모바일 부담 0 | 문제마다 엔진 로딩(§3-2: 파이썬 첫 로딩 수 초), 셀레니움·Colab·MySQL 전용 코드는 실행 불가 |
| 결정성 | 항상 같은 결과 | 세트 출력 순서·난수·플랫폼(int32) 차이로 흔들릴 수 있음 |
| "콜론 빠지면 오답" | 콜론이 빈칸 안에 있으면 목록 비교로 오답 | 실행하면 SyntaxError → 오답 |
| 단점 | 동치 답을 빠뜨리면 맞는 답을 오답 처리 | 무겁고 실행 못 하는 코드가 많다(Lec4 전체, Lec3·Lec5 일부) |

**제안: (A) 허용 답안 비교 + 작성 시 실행 검증(§6).** 빈칸은 한 토큰~한 식 크기로 좁게 만들고, 동치 답은 작성할 때 실제로 실행해 확인한 것만 `accept`에 넣는다. 셀레니움·MySQL 전용 코드도 같은 방식으로 낼 수 있다.

### 2-2. 정규화 규칙 (A안)

- **빈칸 앞뒤 공백만 무시**한다. 빈칸 안에서는 **토큰 단위로 비교**한다 — 토큰 사이 공백 차이는 무시(`range(1,10)` = `range(1, 10)`), 토큰을 붙이거나 나누면 다름(`not in` ≠ `notin`). 파이썬 실행 결과와 같은 기준이다.
- **대소문자**: 파이썬은 구별(`print` ≠ `Print`). SQL은 키워드만 구별 안 함(`SELECT` = `select`), 문자열 값은 구별.
- **따옴표**: 파이썬에서 `'a'`와 `"a"`는 같은 값이라 둘 다 정답. **굽은 따옴표(‘ ’ “ ”)는 채점 전에 곧은 따옴표로 자동 변환**하고, 결과 화면에 "굽은 따옴표를 곧은 따옴표로 바꿔 채점했습니다"를 작게 알린다(결정 13). 슬라이드에 굽은 따옴표 오류가 여러 곳 있다는 점은 해설에 쓸 수 있다.
- **콜론·괄호·세미콜론**: 빈칸에 포함되면 반드시 있어야 정답. SQL 빈칸이 문장 끝을 포함하면 `;`도 필요.
- **들여쓰기**: 빈칸은 들여쓰기 밖(줄 안)에만 둔다. 들여쓰기 자체를 묻는 문제는 `code-write`나 "오류 찾기" mcq로 낸다.
- **부분 점수 없음**: 모든 빈칸이 맞아야 1점, 아니면 0점. 결과 화면에는 칸별 ✓/✗를 보여 준다.
- 모바일 키보드: iOS "스마트 구두점"은 입력 중 `'`를 `’`로 바꿀 수 있다 — 입력칸에 `autocapitalize="off" autocorrect="off" spellcheck="false"`를 두고, 그래도 들어온 굽은 따옴표는 위 규칙대로 자동 변환(결정 13).
- **빈칸 답(`accept`)에는 앞뒤 공백을 넣지 않는다**(결정 12). 입력의 앞뒤 공백은 비교 전에 지운다.

## 3. 전체 작성형 Python `code-write` (Pyodide)

### 3-1. 방식

- **Pyodide를 앱에 직접 포함**(`public/pyodide/` 같은 우리 도메인 경로, 외부 CDN 금지)하고, **코드 작성 문제를 처음 열 때만** 불러온다(다른 화면 번들에 0바이트). Web Worker에서 실행해 화면이 멈추지 않게 하고, 무한 반복은 시간 제한(예: 5초) 뒤 Worker를 종료해 오답 처리.
- 채점 = 테스트 케이스 실행, **전부 통과해야 정답**:
  - **표준 출력 비교**: 줄 끝 개행 하나만 무시하고 나머지는 글자 그대로 비교(공백·대소문자 포함).
  - **변수·함수 값 확인**: 사용자 코드를 실행한 뒤 숨은 검사식을 같은 이름 공간에서 실행(예: `sum_list_r([1, 2, 3]) == 6`, `type(tuple_1) is tuple`).
  - **파일**: CSV·엑셀 문제는 실행 전에 Pyodide 가상 파일 시스템에 `characters.csv` 등을 만들어 두고, 실행 후 파일 내용을 검사.
  - 오류를 기대하는 문제(예: TypeError가 나는 코드 고르기)는 예외 종류로 비교.
- 기존 채점 구조(`QTypeCore.grade`는 동기 함수)와 맞추기: 실행은 화면에서 먼저 하고 결과를 답(`{ source, run: { passed, details } }`)에 담아 넘긴다. `grade`는 담긴 결과만 읽는다 — 기록·통계·오답노트 코드는 그대로.

### 3-3. 결정 (§10-7)

- Python 기본 + openpyxl: 코드 문제를 열 때 Web Worker로 불러온다. 넘파이: 그 문제에 필요할 때만 함께 불러온다. 판다스: 문제 화면의 "실행 엔진 불러오기" 버튼을 눌렀을 때만 내려받는다(용량·예상 시간 안내). 불러오기 전 동작(빈칸형·객관식 변형 vs 제출 불가 안내)은 Sprint 13에서 제안. 엔진 파일은 빌드할 때 npm 패키지에서 `public/`으로 복사하는 방식을 먼저 검토.

초안 당시 제안(참고, 위 결정이 우선):

- **순수 파이썬(Lec1·Lec2) + CSV(표준 라이브러리) + openpyxl(Lec3)**: Pyodide 기본(+0.27 MB)으로 실행 채점. 전송 약 5.8 MB, 첫 로딩 데스크톱 3~5초.
- **넘파이(Lec6 전반)**: 실행 채점을 넣을지 선택(+3 MB, import 2초/모바일 7~13초). 넣는다면 dtype·출력 형식이 플랫폼에 따라 달라지는 문제는 빼고, 값 비교(`np.array_equal` 등) 위주.
- **판다스(Lec6 후반)**: 브라우저 실행 채점은 **넣지 않는 것을 제안**(import 10초, 모바일 25~50초, 메모리 222 MB). 판다스는 `code-blank`, "실행 결과 고르기" mcq(결과는 작성 시 실제 실행으로 고정), `match`(함수 ↔ 역할)로 낸다.

## 4. 전체 작성형 SQL `code-write` (sql.js)

- **sql.js 1.14.2**(SQLite를 wasm으로 빌드한 것)를 앱에 포함: `sql-wasm.wasm` 658 KB(brotli 279 KB) + `sql-wasm.js` 47 KB(brotli 15 KB) — 전송 **약 0.3 MB**, Pyodide보다 훨씬 가볍다. SQL 문제를 처음 열 때만 불러온다.
- 채점 절차: 매 제출마다 **새 데이터베이스**에 고정 준비 스크립트(Lec5 firstDB의 학생·과목·수강 테이블과 데이터, SQLite에서 도는 형태로 바꾼 것 — `#` → `--`, `DEFAULT` 줄은 열 목록 지정으로)를 실행하고, `PRAGMA foreign_keys = ON`을 켠다.
  - **SELECT 문제**: 사용자 결과와 모범 답안 결과를 비교 — 열 개수·값이 같고, **행은 순서 무시(다중집합) 비교**. 문제에 ORDER BY가 요구될 때만 순서까지 비교. 열 이름은 별칭(AS)을 묻는 문제에서만 비교.
  - **INSERT·UPDATE·DELETE 문제**: 실행 후 대상 테이블 전체 상태를 모범 답안 실행 후 상태와 비교.
  - **오류가 나야 하는 문제**(5-26 외래키): 오류 발생 여부만 비교(MySQL `Error 1451`과 SQLite 문구가 다르므로 문구는 비교하지 않음).
- **MySQL과 다른 부분 처리**(`ds-source-analysis.md` §5-3에서 SQLite로 직접 실행해 확인):
  - `CREATE DATABASE`·`USE`, `VALUES(…, DEFAULT, …)`, `SELECT VERSION()`, CHAR 길이 초과 오류, 대소문자 비교 규칙 → **빈칸형·개념 문제로만** 낸다(실행 채점 금지).
  - `#` 주석: 실행 전에 **문자열 밖의 `#`만 `--`로** 바꾼다(결정 8).
  - 행 순서: MySQL은 인덱스 순서로 결과가 나와(5-7: s1·s4·s5·s1·s2·s2·s4) SQLite와 다르다 → 위의 순서 무시 비교로 해결.
  - 날짜: SQLite는 문자열로 저장하지만 'YYYY-MM-DD' 형식이면 비교 결과가 같다(5-18 검증).

## 7. 복수 선택 문제의 정답 2개 이상 강제

- `lib/qtypes/multi.ts`의 `validate`에 "정답은 2개 이상, 보기 수 − 1개 이하"를 추가하면 `data/subjects/integrity.test.ts`가 전 과목 데이터를 검사한다. 현재 데이터는 **OS 24문항·데이터 통신 9문항 모두 정답 2개 이상**이라(2026-10-06 확인) 전 과목에 바로 적용해도 기존 회귀가 깨지지 않는다.

| 11 | 슬라이드 오류 | 정답은 **실제 실행 결과**, 해설에 슬라이드와 다른 점을 **"(보충)"**으로 적는다(2-10 콜론 누락, 출력 표기 차이, 6-40 등). "이 코드에서 오류가 나는 이유/위치" 문제로 활용 가능. **세트 출력 순서처럼 실행마다 달라지는 결과는 출력 문제로 내지 않는다** |
| 12 | 들여쓰기 | 실행 채점에서는 **일관된 들여쓰기면 몇 칸이든 정답.** 빈칸 답(`accept`)에는 앞뒤 공백을 넣지 않는다 |
| 13 | 굽은 따옴표 | 채점 전에 **자동으로 곧은 따옴표로 바꾸고**, 바꿨다는 사실을 결과 화면에 작게 알린다. 코드 입력칸은 `autocorrect`·`autocapitalize`·`spellcheck`를 끈다 |
| 14 | 파란 글자 메모 8개 | 사용자가 **교수님 설명을 받아 적은 수업 필기**다. **출제 근거로 쓸 수 있고**, 해설에 **"수업 필기 기준"**으로 표시한다. ⭐ 근거는 아니다. 노란 형광펜 1개도 같은 기준(`ds-source-analysis.md` §3-2) |
| 15 | 기준 실행 환경 (2026-10-06 추가) | **정답 기준은 슬라이드(Colab, 64비트 CPython) 환경이다.** Pyodide(wasm32)와 결과가 달라질 수 있는 출력(넘파이 dtype·itemsize·nbytes 같은 정수 크기, `sys.maxsize`·`sys.platform`·`id()`·`getsizeof` 같은 플랫폼 의존 표기)은 **출력 문제로 내지 않는다**(개념형으로는 가능 — 예: "64비트 PC에서 `int64`인 이유"). 검증 규칙이 코드(`.dtype` 등)와 실행 출력(`int32`, 메모리 주소)에서 감지해 실패시킨다(`lib/verify/rules.ts`) |
| 16 | 오류 줄 번호 (2026-10-06 추가) | 오류 위치를 묻는 문항의 줄 번호는 **앱 화면에 표시되는 코드(빈 줄 포함) 기준**이다. 코드 전사는 슬라이드의 빈 줄을 보존하고 `lineNumbers: true`로 줄 번호를 보인다. 예: [코드 2-10]은 2번째 줄이 빈 줄이라 콜론이 빠진 `else`는 **12번째 줄** |

## 11. 알려진 한계 (2026-10-07)

- **SQL 전체 작성형은 사용자 답을 sql.js(SQLite)로 실행해 채점한다.** 그래서 MySQL에서는 오류가 나는 문법도 결과가 같으면 정답이 될 수 있다. 채점 결과 화면에 "채점은 sql.js(SQLite)로 실행합니다 — MySQL과 문법 차이가 있을 수 있음"을 한 줄 보여 준다(`components/qtypes/CodeWrite.tsx`). 대표 사례:
  - `SELECT * FROM 학생, 수강 ON 학생.학번 = 수강.학번;` — 쉼표 조인 뒤 ON: SQLite는 실행(WHERE와 같은 결과), MySQL은 문법 오류(Sprint 16 Lec5 join-002 검증에서 발견)
  - 길이를 넘는 값 입력(`CHAR(2)`에 'c10'): SQLite는 그대로 저장, MySQL(엄격 모드)은 오류(`ds-source-analysis.md` §5-3)
  - 문자열 비교 대소문자: SQLite의 `=`는 구별, MySQL 8 기본 정렬은 구별하지 않음 — 대소문자만 다른 값으로 채점하는 문제는 내지 않는다
  - 반대로 MySQL 전용 문법(`CREATE DATABASE`·`USE`·VALUES 안의 `DEFAULT`·`VERSION()`)은 sql.js에서 실행되지 않아 실행 제외 + 빈칸형·개념형으로만 낸다(결정 8, `lib/verify/rules.ts`가 감지)
- 코드 빈칸형은 허용 답안을 토큰으로 비교하므로 이 한계가 없다(엔진을 쓰지 않음). 대신 "같은 결과가 나오는 다른 표현"은 검증 파이프라인이 찾아 accept에 넣은 것만 정답이다.
