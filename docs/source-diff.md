# 소스 PDF ↔ §7 대조 결과 (운영체제 과목)

> PDF 위치는 2026-10-04 다과목 전환으로 `source/` → `source/os/`로 옮겨졌다. 아래 본문의 `source/` 표기는 `source/os/`로 읽는다. 데이터 통신 분석은 [`dc-source-analysis.md`](./dc-source-analysis.md).

`source/` 폴더의 강의 PDF 4개(Ch02/Ch03/Ch07/Ch08)를 `antigravity_prompt_os_exam_app.md`의 §7(챕터별 출제 범위) 및 §6(시뮬레이터 검증 기준값)과 전수 대조한 결과다.

**원칙**: PDF와 §7이 다르면 항상 §7을 따른다. 이 문서는 차이를 기록하는 용도이며, 실제로는 4개 챕터 전부에서 **의미 있는 불일치가 0건**이었다 — §7은 슬라이드(타이핑 본문 + 교수님 손글씨 주석)를 매우 충실하게 반영해 작성되어 있었다.

## 작업 방식 및 도구 이슈

1. 1차로 4개의 조사 에이전트를 병렬로 실행해 각 챕터 PDF를 전부 읽고 §7과 대조시켰다.
2. 이 환경에 PDF 페이지를 이미지로 렌더링하는 `poppler`(`pdftoppm`)가 설치되어 있지 않아, 1차 조사는 챕터별로 결과가 갈렸다:
   - **Ch02**: 문제없이 이미지 렌더링 성공 (손글씨까지 전부 시각 확인).
   - **Ch03**: 이미지 렌더링 실패 → `pdftotext`로 텍스트만 추출(PPT 변환본이라 주석이 텍스트 상자로 들어있어 대부분 커버됨). 화살표/도형 다이어그램은 미확인.
   - **Ch07**: 이미지 렌더링 실패 → `pdftotext`로 추출했으나 한글 다수가 깨짐. 숫자·영문은 보존되어 §6 기준값 대조는 가능했지만 손글씨·그림은 전부 미확인.
   - **Ch08**: 이미지 렌더링 실패 → `pdftotext -layout`으로 추출. 다행히 주석 상당수가 텍스트 상자라 많이 확인됐지만, 그래프·표 숫자는 미확인.
3. 사용자 승인을 받아 `winget install oschwartz10612.Poppler`로 poppler를 설치했다. 다만 이미 실행 중인 호스트 프로세스는 갱신된 PATH를 바로 인식하지 못해, **poppler 바이너리로 직접 PDF 페이지를 PNG로 렌더링한 뒤 그 PNG를 이미지로 읽는 방식**으로 우회했다.
4. 이 방식으로 Ch03/Ch07/Ch08에서 1차 조사가 "확인 필요"로 남긴 핵심 다이어그램들을 **직접 이미지로 재확인**해 대부분 해소했다 (아래 각 챕터 섹션에 반영).

## Ch03. 프로세스 기술과 제어

PDF 45페이지. 1차 조사(텍스트 추출)는 거의 전부 확인했고, 화살표/도형 다이어그램만 미확인으로 남겼던 것을 이미지로 재확인했다.

### 일치 확인 (요약)

§7의 모든 항목이 PDF와 문장 단위로 일치. ⭐ 항목 5곳(종료사유 p.4, 5상태모델 p.13, Suspend p.20-21, 인터럽트처리 p.38-39, Process switch 5가지 p.41-42) 전부 손글씨 "시험"/"무조건 시험" 표기까지 확인됨.

### 불일치

없음.

### 확인 필요 → 재확인 결과

- **p.13 상태 전이도(Figure 3.6 Five-State Process Model)**: 이미지로 직접 확인함. New→(Admit)→Ready→(Dispatch)→Running, Running→(Timeout/Clock interrupt)→Ready, Running→(Event Wait: I/O함수호출 또는 Memory fault)→Blocked, Blocked→(Event Occurs: I/O interrupt)→Ready, Running→(Release: 정상종료 또는 Trap)→Exit. **§7의 전이 서술과 화살표 방향까지 정확히 일치**. 페이지 우측 하단에 "시험" 표기도 확인.
- **p.38 인터럽트 처리 과정**: 이미지로 직접 확인함. 8단계 전부(①발생②Mode switch③벡터링④문맥 PCB저장⑤ISR업무(대기큐→전달→Ready전환→큐이동)⑥scheduler()⑦문맥복구⑧실행) **§7과 순서·내용 정확히 일치**.
- **p.2 오답 보기 문구**("각 프로세서의 정보를 담아놓는 구조체" 류 — 1차 조사에서 OCR 오류로 의심): 콘텐츠 작성 시 이 특정 문구를 그대로 재사용하지 않고, §7이 명시한 취지(전역변수 등 프로세스와 무관한 오답)로 새로 작성하기로 함 — **최종적으로 "확인 필요" 유지, 추측 금지**.
- **p.13 손글씨 "각+ㅏ:기존 각 지우고 가가로"**: 맥락이 끊긴 낙서/도형 편집 지시로 추정되며 §7에 영향 없음. **"확인 필요" 유지하되 콘텐츠에는 영향 없음으로 처리**.
- **'잘못된 명령(invalid instruction)'의 처리 결과** (Sprint 5 작성 중 발견, 슬라이드 내부 불일치): p.4는 인쇄로 '잘못된 명령(invalid instruction) 실행'을 종료 사유 목록에 넣었지만 필기는 "운영체제가 죽이진 않고 보통 프로그램이 에러메시지를 줌"이다. p.42 인쇄 본문은 Process switch 4번 Trap interrupt의 예로 "Illegal instructions(명령어가 깨졌을 때, CPU)" → Exit state로 전환하고 현 프로그램 종료다. 결정(2026-10-05 사용자 확인): **종료 사유 맥락(p.4)에서는 출제 보류**, **Process switch 맥락(p.42)에서는 출제** — 근거를 p.42로만 쓰고 p.4와 섞지 않는다. 해당 문항: `os-ch03-process-switch-001·003·004·005`(`data/subjects/os/ch03.ts` 머리 주석).

## Ch07. 메모리 관리

PDF. 1차 조사(텍스트 추출, 한글 깨짐)는 숫자·영문 중심으로 §6 기준값을 확인했고, 손글씨·그림은 전부 "확인 필요"로 남겼던 것을 이미지로 재확인했다.

### 일치 확인 (요약)

§7의 모든 항목이 슬라이드와 일치. §6-1(paging)·§6-2(segmentation) 기준값 숫자 전부 슬라이드와 **정확히 일치** (p.32-36).

### 불일치

없음.

### 확인 필요 → 재확인 결과 (이미지로 전부 해소)

- **p.16 배치 알고리즘**: "네가지 케이스 시험" 손글씨 확인. Best-fit 설명·"성능이 가장 나쁨"·"메모리 압축을 더 자주 해야 함" 등 §7과 일치.
- **p.21 버디 시스템 할당**: 좌측 상단 "시험" 표기 확인. "40bytes 요청→2^6(64) 할당", "비어있는 64 블록 없으면 128을 반으로 분할해 왼쪽 할당", "같은 크기로 분할된 두 블록끼리 buddy", "파란색 64와 검은색 64는 친구가 아님" 등 §7 서술과 전부 일치.
- **p.22 버디 반납/병합** 규칙 설명 확인, §7과 일치.
- **p.23 — ⭐ 버디 1MB 전체 트레이스 표가 실제로 존재함을 확인.** "시험. 메모리 할당하는 과정이 시험에 나옴" 손글씨 포함. 표 내용을 전사하면:
  - `1 Mbyte block: 1M`
  - `Request 100K: A=128K | 128K | 256K | 512K`
  - `Request 240K: A=128K | 128K | B=256K | 512K`
  - `Request 64K: A=128K | C=64K | 64K | B=256K | 512K`
  - `Request 256K: A=128K | C=64K | 64K | B=256K | D=256K | 256K`
  - `Release B: A=128K | C=64K | 64K | 256K | D=256K | 256K`
  - `Release A: 128K | C=64K | 64K | 256K | D=256K | 256K` (주석: "Release될 땐 합병을 시켜야함. 현재는 비어있지 않으므로 하고싶어도 못함" — A의 buddy인 128K 블록이 C+64K로 **split된 상태**이므로 둘 다 free라도 merge 불가. 버디 병합은 "buddy가 쪼개지지 않은 채 free"일 때만 가능하다는 중요 규칙)
  - `Request 75K: E=128K(=A자리 재사용) | C=64K | 64K | 256K | D=256K | 256K`
  - `Release C: E=128K | 128K(C+64K 병합) | 256K | D=256K | 256K`
  - `Release E: 512K(E+128K+256K 병합) | D=256K | 256K`
  - `Release D: 1M(전체 병합)`
  - 이는 md §6-3의 중간상태(A=[0,128K), B=[256K,512K), C=[128K,192K), D=[512K,768K))와 **완전히 일치**하며, md보다 더 상세한 단계별 표까지 확보했다. **Sprint 4에서 이 표를 그대로 `buddy.ts` Vitest 기준값으로 사용 가능.**
- **p.24 — "트리 구조 필요" 서술의 슬라이드 근거 확인됨.** Figure 7.7 "Tree Representation of Buddy System" 그림이 실제로 존재하며, Request 256K 시점의 트리(1M→512K×2→256K(분할)+256K(free)→128K(A, free좌/분할우)→64K(C,free)) 상태를 보여준다. 하단 주석: "메모리 할당 관리하려면 트리구조를 내부적으로 가지고 있어야지 메모리 할당 상태를 정확하게 추적해서 합병을 할 수 있다." — §7 문구와 정확히 일치. **버디 블록 두 개가 모두 free라도, 같은 split에서 나온 buddy 쌍이 아니면 병합 대상이 아니라는 것**이 이 그림과 p.23의 Release A 주석이 공통으로 보여주는 핵심 규칙이며, `lib/sim/buddy.ts` 구현 시 반드시 트리(또는 등가 구조)로 분할 계보를 추적해야 함.
- **p.32 "주소 변환"**: 세 가지 문제 유형("①페이지테이블+논리주소→실제주소 ②페이지테이블+실제주소→논리주소 ③논리·실제주소로 프레임번호 결정")이 슬라이드 제목 바로 아래에 그대로 적혀 있음을 확인 — §7 서술의 직접적 근거. 페이지크기 1000 예시(논리1,179→페이지1·offset179·프레임5→물리5,179)도 그림으로 확인, **§6-1 기준값과 완전 일치**.
- **p.33 비트 슬라이싱**: 16비트 논리주소, 6비트 page#/10비트 offset(2^10=1024) 그림 확인 — §6-1의 "16비트 논리주소, 1KB 페이지 → 상위 6비트, 하위 10비트" 서술과 **정확히 일치**.

- **Sprint 6 문제 작성 중 추가 확인(2026-10-05)**:
  - p.23 필기 "만약 256을 할당받으면 어느쪽을 할당받나?" — 그 시점(Request 75K 직후) 빈 256K 블록이 [256K,512K)·[768K,1024K) 둘이고 어느 쪽을 쓰는지 슬라이드에 답이 없다. `buddy.ts`의 "같은 크기면 낮은 주소" 규칙은 구현 규칙일 뿐이라 **출제 보류**(p.21의 "분할 후 왼쪽 반 할당"은 인쇄 규칙이라 출제).
  - p.21 상단 필기 "동적으로 메모리를 할당하는 알고리즘은 버디 알고리즘을 더 성능이 좋게 개선시킨것이다" — p.11 인쇄(버디 = 고정·동적 분할의 절충)와 방향이 엇갈려 **출제 보류**.
  - **"물리→논리 변환은 선형 탐색이라 느리다" — 요구사항 §6-1·§7에는 있으나 슬라이드에 없음.** p.32-36을 이미지로 재확인(2026-10-05): p.35 인쇄는 "page table에서 프레임 번호(2) 값을 가지는 index(1) 찾음 / 이 index 값이 페이지 번호(1)임"까지이고, '선형 탐색'·'느리다'는 인쇄·필기 어디에도 없다. 주소 변환 페이지의 속도 관련 필기는 p.33 "곱하기 나누기로 하면 시간이 오래걸림"(비트 분해 이야기) 하나뿐이다. 해당 문항(`os-ch07-translation-002·006`, `os-ch07-gen-paging-1`)은 해설에 **(보충)** 유지.
  - p.33 필기 "곱하기 나누기로 하면 시간이 오래걸림", p.41 필기 "유일한 차이: 세그먼트 번호가 아닌 세그먼트 시작주소", p.12 필기(16M 분할에 13M → 3M 놀고 있음, 많이 쓰는 8M는 2개) 확인 — 문항에 "교수님 필기 기준"으로 반영.

## Ch08. 가상 메모리
